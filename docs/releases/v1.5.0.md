# Topophany v1.5.0

Released October 23, 2026.

Topophany 1.5.0 adds Komari resource collection and direct profiles without a
collector. It also improves durable worker delivery, collector failover and
evidence recovery. Verify downloads against `SHA256SUMS.txt`.

## Changes since 1.4.2

- **Komari resources.** The read-only adapter supports the pinned Komari 1.6.0
  response schema through `GET /api/recent/<uuid>`, with API-key or anonymous
  access. It selects the newest valid upstream report, preserves exact byte
  counters and stable sample identity, and maps CPU, memory and aggregate disk
  capacity. Collection is bounded and atomic across selected nodes. Empty or
  failed reads never become proof of a target outage.
- **Komari direct profiles.** `topo sources inspect|save|list|remove` supports
  Komari keys, environment references, saved credentials and anonymous public
  nodes. The same profile works in the resource TUI, status, show and monitor
  commands without a collector or daemon, and can mix Beszel and Komari sources.
  Discovery verifies administrator keys through the protected client-list
  endpoint without falling back to guest access.
- **Durable delivery and failover.** Worker outboxes reserve byte and record
  capacity per recipient. Authorization outages keep pending evidence available
  for retry, while explicit payload rejections isolate only the refused member
  of a fan-out item. Viewer reads reserve time for a backup collector and move
  scoped/global snapshot pairs together.
- **Evidence, capacity and reloads.** Worker-local panels retain external
  reports and expire them at their original deadlines. Collector startup and
  reload preflight complete external replay reservations. Direct views update
  only changed evidence and reuse unchanged acquisition state. Changes to
  staleness rules rebuild confirmation from available samples, and invalid
  adapter reloads preserve the running configuration.
- **Transport and output safety.** Source and discovery transports close on
  every exit, including canceled TLS handshakes. Direct retries cover HTTP 408
  and all 5xx failures. Discovery rejects credential-bearing identities and
  redacts every session credential before truncation; source commands share
  terminal-safe JSON output. Monitor shutdown and bounded Windows ACL startup
  are covered by regressions.

## Compatibility and upgrades

Upgrade the collector, workers and viewers before enabling Komari bindings;
upgrade the local binary before using Komari direct profiles. Komari is a
resource-only adapter: online presence and per-filesystem disks are unsupported.
Use `external.primary_disk: "aggregate"`, not `"root"`. The recent endpoint
retains about one minute of reports; a 30-second polling interval reduces missed
reporting bursts. Its future removal or a changed response schema fails
explicitly; support is pinned to Komari 1.6.0.

Komari API keys have administrator authority upstream even though Topophany
performs only the documented reads. Supply the raw key through the configured
environment reference or direct JSON stdin. Keys are nonrenewable; a changed
environment key requires an explicit inspect/save. Anonymous reads cover public
nodes only. Direct profiles remain private and keep no resource history.

Topology schema 1, batch/snapshot schema 3, checkpoint schema 2 for external data,
monitor protocol 1 and `direct.schema=1` remain unchanged from 1.4.2. Detect Komari
support through the direct adapter capabilities. Existing native measurement
contracts are unchanged. Upgrades from 1.4.1 or earlier must also follow the
[1.4.2 schema migration notes](https://github.com/WhitenWhiten/topophany/blob/v1.5.0/docs/releases/v1.4.2.md#compatibility-and-upgrades).

Back up collector data and worker outboxes before upgrading. Outbox pending byte
and record budgets now divide equally among configured recipients, charging each
pending destination independently. Drain or archive legacy backlogs that exceed
a destination's share before starting the upgraded worker. HTTP 401/403 pauses
delivery with bounded retries and retains pending samples; repair authorization
and restart the worker if its saved credentials changed.

External collector state can grow to 128 MiB within the existing global budget;
startup, reload and `topo capacity` reserve complete replay windows. Older
binaries enforce a 4 MiB external-state recovery limit and cannot reopen a larger
checkpoint. Direct state now allows 32 MiB per profile and 4 MiB per source in a
multi-source profile. Keep a matching backup for rollback rather than assuming
that unchanged schema numbers imply older capacity limits can read all state.

Confirmation carries now record the staleness rules they were folded under.
Legacy carries with unknown rules, or carries after a staleness-rule change,
rebuild from retained samples; checks can temporarily need fresh evidence to
confirm their state. Presentation edits and supported threshold changes retain
compatible confirmation. See the
[reference](https://github.com/WhitenWhiten/topophany/blob/v1.5.0/docs/REFERENCE.md)
and [operations guide](https://github.com/WhitenWhiten/topophany/blob/v1.5.0/docs/OPERATIONS.md).

## Acceptance scope

The automated suite covers Komari through synthetic loopback endpoints and the
production runner, outbox, collector, store, views and monitor. It exercises
sample identity, exact counters, authentication boundaries, cancellation,
credential reflection, restart/replay, expiry and direct profile commands.
CI and release builds require the real old-reader compatibility test to execute
and pass. The optional official Komari binary harness uses a disposable loopback
server and synthetic Agent v2 samples; it is separate from offline acceptance.
No compatibility with arbitrary future Komari versions or production deployment
acceptance is claimed. Cross-builds verify compilation for each target.

## Downloads

Choose `topophany_1.5.0_<os>_<arch>`: `.tar.gz` for Linux and macOS, `.zip` for
Windows. macOS is `darwin`; Apple silicon is `arm64`, and Intel or AMD 64-bit
systems are `amd64`. Each archive contains `topo` (`topo.exe` on Windows), the
license, the three READMEs and the changelog. `topo version` should report
`Topophany 1.5.0`. Source builds require Go 1.26.10 or newer.
