# Topophany v1.4.0

Released October 20, 2026.

Topophany 1.4.0 adds deeper Cloudflare support from the public edge to local
Tunnel connectors and read-only API reports, and a service card mode for the
terminal and desktop widgets. Verify downloads against `SHA256SUMS.txt`.

## Changes since 1.3.0

- **Cloudflare response evidence.** HTTP checks recognize challenge pages and
  Access login redirects, read optional edge TCP/QUIC timing from `cfL4`, and
  explain Cloudflare error responses without declaring the origin at fault.
  Access service-token headers can come from the worker's environment through
  `request_header_envs`, keeping secret values out of the topology.
- **Trace and policy.** `/cdn-cgi/trace` reports WARP, Gateway, colo and protocol
  information. `expected_trace` and `expected_pops` flag departures from your
  declarations as policy violations. DNS checks support TCP, DoT and DoH in
  addition to the existing UDP transport.
- **Tunnel and API reports.** The `cloudflared` check reads the local connector's
  `/ready` and `/metrics`. The `cloudflare` check uses a scoped API token for
  Tunnel status, DNS records or load-balancer pool health. Connector readiness,
  public edge responses and application health stay separate, with monitor
  errors distinguished from outages.
- **Colos and history.** Maps place fresh Cloudflare response colos using a
  bundled location table, with hollow markers for reported locations. Daily
  rollups show colo/cache shares and cached versus origin-class first-byte
  timing, also used in server cards and observer evidence.
- **Service card mode.** Press `s` on Services for a uniform grid grouped by
  application and colored for the host. Each card shows who checks the service,
  recent samples, daily latency and uptime, addresses, dependencies and edge
  colos. `Enter` opens its checks, cache shares, notes and runbook. Start with
  `topo --page services --service-cards`; the preference persists.
- **Service cards in widgets.** Monitor templates and `topo monitor stream` add
  `service.card` (`select.service`) and `services.list`, with independent check
  deadlines and up to 40 recent samples per check.
- **Release and telemetry hardening.** Releases build into fresh directories,
  validate exact archive manifests and check the source tag before publishing.
  Credential-reflecting numeric responses are withheld, monitor rows share
  output budgets, and cross-observer response indexing is bounded.

## Compatibility and upgrades

Upgrade collectors and all viewers before adding the new Cloudflare adapter
options, DNS transports, `request_header_envs`, `expected_trace` or
`expected_pops`; older binaries reject those measurement contracts. Upgrade
workers before asking them to run the new checks. Existing topologies without
these fields retain their measurement hashes.

`Host` request headers now reject values the HTTP transport would drop or
refuse, including malformed ports, unbracketed IPv6 and raw non-ASCII names.
`bearer_env` and `request_header_envs` variable names must be 1..128 bytes and
contain no `=`, comma, whitespace, control or bidi characters. Check existing
custom headers and variable names before upgrading. A configured `User-Agent`
now takes precedence over Topophany's default.

The monitor stream protocol stays at 1. Check the metric catalog before
requesting `service.card` or `services.list` from an older binary. Rollup fields
are additive within schema 1: older binaries ignore them and older checkpoints
have no such readings. No journal or checkpoint migration is required.

## Acceptance scope

Cloudflare API fixtures are synthetic and based on documented response shapes;
no live account or API token was used. Local connector acceptance used
cloudflared 2026.10.0 with a fake, unregistered tunnel. Successful connected
responses remain synthetic. See the
[API acceptance record](https://github.com/WhitenWhiten/topophany/blob/v1.4.0/docs/acceptance/CLOUDFLARE_API_2026-10-19.md)
and [connector acceptance record](https://github.com/WhitenWhiten/topophany/blob/v1.4.0/docs/acceptance/CLOUDFLARED_2026-10-19.md).
Preview failure scenarios are simulated. Cross-builds establish compilation,
not native runtime acceptance on every archive architecture.

## Downloads

Choose `topophany_1.4.0_<os>_<arch>`: `.tar.gz` for Linux and macOS, `.zip` for
Windows. macOS is `darwin`; Apple silicon is `arm64`, and Intel or AMD 64-bit
systems are `amd64`. Each archive contains `topo` (`topo.exe` on Windows), the
license, the three READMEs and the changelog. `topo version` should report
`Topophany 1.4.0`.
