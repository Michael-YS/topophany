The latest follow-up measurements are in [compact state and streaming recovery](#follow-up-compact-live-state-and-streaming-recovery): 59.7 MiB collected heap and 127.7 MiB recovery/checkpoint peak RSS with the unchanged 128 MiB soft target.

The running deployment was inspected through existing SSH connections. Production
services, their configuration, and retained evidence were not changed. A new
local binary is available as `bin/topo`; it has not replaced the installed binary.
Measurements below are samples, not a continuous production leak test.

## Changes

- State evaluation uses bounded per-check tails and carries; legacy observations
  and callers lacking installed contracts retain their compatible history path.
- Pruning reuses the history allocation rather than allocating a full replacement
  for every sample, and clears unused history elements and expired queue IDs.
- Checkpoints and rollups stream records into an atomic temporary file. The
  checksum is patched before fsync and publication; the existing envelope and
  schema remain readable. Failed producers preserve the old checkpoint.
- Checkpoint recovery avoids a payload-sized RawMessage copy, byte/string hash
  copies and geometric whole-file input-buffer growth.
- Worker delivery detaches at most about 1 MiB of pending records per cycle
  (always allowing one record to progress), and encodes each candidate's
  observations once rather than serializing the growing batch repeatedly.
- `serve`/`worker` now offer soft Go targets, Linux kernel caps, and minute-level
  GC-live-heap/runtime/goroutine diagnostics. New Linux units have 256 MiB
  collector / 128 MiB worker hard budgets with swap disabled. See
  [Memory budgets](../MEMORY.md) for flags and limitations.

## Leakage and verification limits

A fixed four-check synthetic workload advanced five days across 120 receipt
expiry windows, rollup saturation and compaction. Collected heap at daily
checkpoints was 927,152; 907,944; 888,536; 865,256; and 936,216 bytes. Receipts
stabilized at 52 and raw history at four rows. State indexes remained bounded.
This is evidence that these storage paths plateau; it cannot prove that every
adapter, network failure, reload pattern or production workload is leak-free.
The sampled worker figures also do not establish a long-term absence of leaks.

Validation completed:

- Full Go suite and `go vet ./...`.
- Race tests for app, store, rollup, outbox, secure, API, bootstrap and memlimit.
- Linux amd64 and Windows amd64 builds; native macOS build and flag checks.
- Checkpoint checksum, restart, history, policy and failure-carry regressions;
  failed streamed-write durability; streamed rollup schema equivalence; delivery
  byte-bound and detached-ownership tests.
- A native Linux kernel test on Huawei in a fresh private cgroup. A test child
  started with a 128 MiB cap, requested 64 MiB through the implementation, then
  attempted to retain 256 MiB despite a 32 MiB Go target. It was SIGKILLed and
  `memory.events` recorded an OOM kill. The test passed in about 0.05 seconds;
  its temporary executable and cgroup were removed. The existing worker PID
  remained running. The same acceptance test is included in Linux CI.

Hard enforcement currently requires Linux cgroup v2. macOS and Windows reject a
requested `--memory-max`; their Go memory targets remain soft. Existing services
must be upgraded and configured explicitly before any of these changes apply.

## Follow-up: compact live state and streaming recovery

A second optimization pass kept the same checkpoint, sample rates, retained raw
history and deduplication semantics. Tests read a frozen copy with 96,277
receipts, 19,998 raw rows and 78 current tails. No production service was
replaced or restarted.

| Implementation | Go soft target | Collected heap after checkpoint | Process maximum RSS |
| --- | --- | ---: | ---: |
| First optimization pass | 128 MiB | 79.2 MiB | 158.1 MiB |
| Second pass | 128 MiB | 59.7 MiB | 127.7 MiB |
| Second pass | 96 MiB | 59.7 MiB | 112.9 MiB |

These fresh native test processes ran sequentially after the other test suites
finished, using the same `/usr/bin/time -l` recovery/checkpoint measurement as
above. The live heap fell about 25%; maximum RSS with the same soft target fell
about 19%. A 96 MiB target is an optional tradeoff, not a new default or a hard
RSS guarantee. Go CPU time for this cached recovery/checkpoint sample was about
1.42 seconds before, 0.66 seconds after at 128 MiB and 0.81 seconds at 96 MiB;
these short local samples are not a throughput guarantee for a small VPS.

The second pass changed only representation and recovery:

- SHA-256 receipt and row fingerprints are stored as 32 bytes internally rather
  than allocated 64-character strings. Checkpoint JSON still uses the original
  hexadecimal strings, so the schema and full hash precision are preserved.
- Repeated observation fields, diagnostic text, fact keys/values and timing
  keys share immutable strings. A two-generation dictionary has at most 4,096
  entries in each generation, excludes values longer than 256 bytes, and rotates
  under changing diagnostics. Mutable fact/timing maps remain detached.
- Rollup recovery allocates known bucket, boundary and histogram lengths directly
  rather than retaining spare capacity from repeated append growth.
- Checkpoint recovery streams rows and receipts directly into the store, avoiding
  a full input-file buffer and a duplicate decoded history. A second bounded file
  pass verifies the exact original payload bytes before the journal opens. State
  carries are installed before rebuilding tails, independently of JSON field order.
- A small checkpoint starts with a small history allocation, and excess recovery
  capacity is discarded. Streaming output also avoids allocating byte slices for
  repeated punctuation and checksum strings.

A five-iteration checkpoint benchmark allocated 49,543,070 bytes/op and took about
126 ms/op, compared with approximately 54.7 MB/op and 128 ms/op for the first
pass. These allocation counts are distinct from process peak memory.

The full suite, vet, Linux/Windows builds, and store/rollup/API/app race suites
passed. Added tests cover legacy hexadecimal receipt JSON (including escapes),
whitespace and reordered checkpoint fields, unknown nested fields, checksum and
truncation refusal before journal open, historical failure carries, UTF-8 byte
budgets, string-sharing ownership and bounded dictionary churn. The five-day
synthetic soak also exercises continuously changing diagnostics: daily collected
heap was 1,185,192; 1,539,120; 1,809,624; 1,587,688; and 1,877,784 bytes as the
bounded dictionary warmed and rotated, with 52 receipts and four raw rows. The
soak passed both normally and under the race detector. It does not establish
that every production workload is leak-free.

The main remaining state consists of the retained observations, receipt lookup
index and rollups. Substantially smaller budgets would require a further change
in their representation or disk-backed lookup, with separate query and recovery
performance validation.
